## 1. Корректность метода и достаточность выборки

### Корректность метода

Метод логически корректен: если H0 утверждает disjointness policyURI-наборов между courts, то нахождение хотя бы одного общего URI опровергает H0. Это валидная логика.

Однако есть нюанс:
- H0 сформулирована как «policyURI-наборы disjoint». Это сильная формулировка. В реальности disjointness — редкое свойство. H0, по сути, невозможна a priori, если существует хотя бы один общий шаблон.
- H1 сформулирована как «этапы одной эволюционирующей программы». Это уже интерпретация, а не просто отрицание H0.

### Достаточность выборки

Для опровержения H0 (disjointness) достаточно одного контрпримера. В этом смысле 20 из 87 и 20 из 36 — более чем достаточно.

Но для поддержки H1 («одна программа») выборка недостаточна:
- 20/87 (23%) для court 29 — низкая coverage. Могут существовать URI, уникальные для court 29, которые не попали в выборку.
- 20/36 (55%) для court 32 — приемлемо, но все еще не полное покрытие.
- Для court 34 использовались 135 disputes из Run 014 (полная выборка или существенная часть).

Рекомендация: если возможно, проверить полноту — все ли URI court 29/32 покрыты, или есть уникальные.

## 2. Надёжность пересечения policyURI как доказательства

### Пересечение URI опровергает disjointness — это факт.

### Но пересечение URI ≠ одна программа.

Альтернативные объяснения:

**A. Общий шаблон-библиотека.**  
Kleros может иметь стандартные шаблоны (например, «consumer dispute template»), которые используются разными операторами в разных courts. policyURI — это content identifier, не program identifier.

**B. Форк шаблона.**  
Если URI указывает на IPFS content, один и тот же CID означает идентичный контент. Но разные программы могут использовать один и тот же шаблон как boilerplate.

**C. Маркетплейс / shared template.**  
Если DisputeResolver или Kleros предоставляет готовые шаблоны, разные courts могут использовать общие шаблоны без связи между программами.

**D. Court migration с сохранением шаблона.**  
Если программа мигрировала из court 29 в 32 в 34, она могла сохранить тот же шаблон. Это поддерживает H1, но требует дополнительного доказательства (например, temporal ordering).

**E. Разные программы, один шаблон.**  
Возможно, court 29 — это программа A, court 32 — программа B, court 34 — программа C, но все они используют шаблон «Spanish consumer dispute» из общей библиотеки.

## 3. Подмена вывода — ключевой вопрос

### Да, есть подмена вывода.

**Фактическое наблюдение:** «Один и тот же policyURI встречается в disputes разных courts.»

**Вывод в Run 018:** «Три волны — этапы одной эволюционирующей программы.»

**Проблема:**  
Это не единственно возможная интерпретация. Другие интерпретации:
- Общий шаблон используется разными независимыми программами.
- Один оператор использует разные courts для разных типов дел, но с общим шаблоном.
- Kleros предоставляет стандартные шаблоны, которые не привязаны к конкретной программе.
- Шаблон — это policy (правила), а не program (инициатор/оператор).

**Что нужно для поддержки H1:**
- Идентификация оператора (off-chain): кто создает дела?
- Идентичность arbitrable contract across courts (уже есть: один DisputeResolver).
- Temporal ordering: disputes в court 29 закончились до начала court 32?
- MetaEvidence или DisputeTemplate, указывающие на конкретную программу/платформу.
- Fee token / economic pattern: одинаковый токен оплаты, одинаковые суммы?

## 4. Что пропущено

### A. Temporal analysis
Не указано, есть ли временной gap между волнами. Если court 29 активен до court 32, а court 32 до court 34 — это поддерживает H1. Если они перекрываются — это противоречит H1 (одна программа не может одновременно быть в разных courts с разными policy, если policy определяет court).

### B. DisputeTemplate vs policyURI
В Kleros V2 `templateId` — это ссылка на DisputeTemplateRegistry, а `policyURI` — это off-chain content. Нужно проверить, используется ли один и тот же `templateId` в разных courts. Если да — это более сильное доказательство, чем policyURI (CID может быть общим, templateId — уникален для программы).

### C. ExtraData / court encoding
В `createDispute` `extraData` кодирует courtId. Если один и тот же arbitrable (DisputeResolver) создает дела в разных courts, это может быть:
- осознанный выбор оператора (разные типы дел в разные courts);
- изменение конфигурации программы;
- миграция всей программы.

Нужно проверить, менялся ли `extraData` encoding для одного и того же шаблона.

### D. Operator identity
Кто инициирует дела? Lemon? Seer? Другой интегратор? Без этого «программа» остается абстракцией.

### E. Court parameters change
Возможно, courts 29, 32, 34 — это не разные программы, а один court, который менял ID (redeployment, upgrade, fork). Нужно проверить `CourtCreated` events для этих courts.

### F. Fee token analysis
Если все дела в трех волнах оплачены одним токеном (например, DAI) одним способом — это поддерживает H1. Если разными — противоречит.

## 5. Следующий шаг

**Рекомендация: (b) причина миграции между courts + (a) идентификация оператора.**

### Почему не (c) Resource Fit

Resource Fit преждевременен, пока не понятно:
- что есть «программа» (одна или три?);
- кто оператор;
- почему миграция.

### Почему (b) + (a)

**Шаг B1 — Temporal + Parameter analysis:**
- Проверить `lastPeriodChange` для disputes в courts 29, 32, 34.
- Есть ли gap? Перекрываются ли периоды активности?
- Проверить `CourtCreated` events для courts 29, 32, 34 — когда они были созданы?

**Шаг B2 — TemplateId analysis:**
- Получить `templateId` для disputes с общими policyURI.
- Совпадают ли templateId across courts?
- Если templateId одинаковый — это сильное доказательство единой программы.
- Если разный — общий шаблон, разные программы.

**Шаг A1 — Operator identification:**
- Проверить `arbitrated` address в `DisputeCreation` events.
- DisputeResolver — это gateway. Кто вызывает `createDispute` на DisputeResolver?
- Трассировать `msg.sender` через transaction logs.

**Шаг A2 — Off-chain correlation:**
- Если policyURI указывает на IPFS/Arweave content, извлечь и проверить, содержит ли он указание на оператора (Lemon, Seer, etc.).

### Итог

Run 018 корректно опровергает H0 (disjointness), но вывод H1 («одна программа») — это hypothesis, требующая дополнительного подтверждения. Пересечение policyURI — необходимое, но недостаточное условие. Нужны templateId, temporal ordering, operator identity и fee pattern для повышения уверенности.
