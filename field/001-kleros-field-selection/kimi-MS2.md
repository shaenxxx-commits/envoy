### Оценка кандидатов

#### 1. UDRP (Uniform Domain-Name Dispute-Resolution Policy)

**FACT:**
- Существует централизованная система арбитража доменов через ICANN-аккредитованные провайдеры (WIPO, NAF, ADR.eu и др.)
- Публично доступные решения арбитражных панелей публикуются на сайтах провайдеров
- Правила документированы (UDRP Policy, Rules for UDRP)

**OBSERVATION:**
- Объём корпуса: тысячи решений доступны для анализа
- Структура решений относительно стандартизирована (жалобщик, ответчик, панель, тесты)
- Существующая литература фокусируется на правовом анализе, не на паттернах принятия решений

**HYPOTHESIS:**
- Внутри UDRP существуют скрытые паттерны в интерпретации "bad faith" и "legitimate interests", которые не отражены в явных правилах
- Различия между провайдерами (WIPO vs NAF) могут быть систематическими, а не случайными

**UNKNOWN:**
- Точный объём и качество машиночитаемых данных (HTML vs структурированные данные)
- Степень консистентности между различными панелистами
- Наличие API или массового доступа к данным

**Поддерживаемое:** Публичная доступность, чёткие границы корпуса, возможность сравнительного анализа провайдеров

**Структурный исследовательский вопрос:** Как неявные факторы (национальность сторон, выбор провайдера, состав панели) влияют на исход при формально идентичных правовых основаниях?

**Практическая/ресурсная возможность:** Повторяемость анализа, сравнение "предсказаний" модели с фактическими решениями, низкий порог входа

**Препятствие:** Необходимость скрейпинга и нормализации разнородных форматов публикаций; потенциальные ограничения на bulk-доступ

---

#### 2. Specific types of domain disputes

**FACT:**
- UDRP — не единственный механизм (также существуют национальные суды, URS для новых TLD)
- Различные категории: cybersquatting, typosquatting, domain warehousing, reverse domain hijacking

**OBSERVATION:**
- "Типы" определены через юридическую классификацию, не через эмпирические паттерны
- Существующие базы данных (например, WIPO Case Management System) имеют категоризацию, но её качество UNKNOWN

**HYPOTHESIS:**
- Эмпирическая кластеризация решений выявит типы, не совпадающие с юридическими категориями (например, "комплексные споры с конкурирующими legit interests" vs "очевидный bad faith")

**UNKNOWN:**
- Какие именно "типы" имеются в виду в описании кандидата
- Существуют ли готовые размеченные датасеты по типам споров
- Границы между типами (fuzzy или дискретные)

**Поддерживаемое:** Потенциал для подтверждаемой типологии

**Структурный исследовательский вопрос:** Можем ли мы построить воспроизводимую типологию споров на основе фактических паттернов, а не юридических дефиниций?

**Практическая/ресурсная возможность:** Возможность создания инструмента предварительной классификации новых споров

**Препятствие:** Необходимость ручной разметки или нечётких границ; риск tautology (классификация по исходу, а не по признакам)

---

#### 3. New TLD domain disputes

**FACT:**
- Процесс new gTLD (2012-2017) создал сотни новых доменов верхнего уровня
- Существует специфический механизм URS (Uniform Rapid Suspension) для новых TLD
- TMCH (Trademark Clearinghouse) — система предварительного уведомления

**OBSERVATION:**
- New TLD породили новые категории споров: contention sets, geographic names, community objections
- Данные о спорах в new TLD существуют, но распределены между различными базами (ICANN, провайдеры URS)

**HYPOTHESIS:**
- Споры в new TLD имеют качественно другую структуру: больше многозаявительных ситуаций, сложнее определение правообладания, новые формы "bad faith"

**UNKNOWN:**
- Объём и доступность данных URS по сравнению с UDRP
- Степень пересечения между UDRP и URS (одни и те же споры в разных системах?)
- Временные рамки: актуальность vs историчность

**Поддерживаемое:** Чёткая временная граница (пост-2012), новизна правовых вопросов

**Структурный исследовательский вопрос:** Являются ли механизмы разрешения споров в new TLD эффективными для их специфических проблем или переносом старых паттернов на новый контекст?

**Практическая/ресурсная возможность:** Меньший объём данных (управляемый корпус), возможность сравнения pre/post new TLD

**Препятствие:** Разнообразие типов споров (не только cybersquatting, но и contention, geographic, community) может размыть фокус; данные URS менее стандартизированы чем UDRP

---

#### 4. Kleros / crypto arbitration

**FACT:**
- Kleros — децентрализованная платформа арбитража на Ethereum, использующая механизм crowdsourced jurors
- Данные о кейсах публичны (blockchain + IPFS)
- Существуют и другие платформы (Aragon Court, и т.д.)

**OBSERVATION:**
- Структура споров принципиально иная: не доменные имена, а "generic oracle" для различных контрактов
- Механизм стимулирования жюри (token economics) — ключевой отличительный элемент
- Существующий корпус значительно меньше UDRP (сотни vs тысячи кейсов)

**HYPOTHESIS:**
- Паттерны голосования в Kleros могут быть предсказуемы на основе характеристик жюри, стейка, типа спора
- Экономические стимулы могут создавать систематические искажения, невидимые в традиционном арбитраже

**UNKNOWN:**
- Детальная структура доступных данных (какие метаданные присутствуют в публичных записях)
- Возможность восстановления полной истории голосований (privacy vs transparency trade-offs)
- Правовой статус решений Kleros (enforceability, recognition)

**Поддерживаемое:** Полная прозрачность данных (blockchain), новизна механизма

**Структурный исследовательский вопрос:** Как экономические стимулы и рандомизация выбора жюри влияют на сходимость к "истине" vs консенсусу? Можно ли обнаружить систематические смещения в зависимости от типа спора?

**Практическая/ресурсная возможность:** API/blockchain access для автоматизированного сбора; возможность "live" тестирования (новые кейсы генерируются регулярно)

**Препятствие:** Меньший объём данных; сложность в определении "ground truth" для оценки качества решений; технический порог входа (blockchain инфраструктура); неопределённость правового статуса как арбитража

### Рекомендация приоритета

**Первый приоритет: UDRP**

**Обоснование:**
- Наибольшая зрелость по критерию CORPUS BOUNDARY — чёткое определение что входит и не входит в поле
- Достаточный объём данных для статистической значимости без неуправляемого разрастания
- Наличие незавершённого синтеза: юридическая литература существует, но количественный анализ паттернов — нет
- Практическая ценность подтверждена: система действует, возможность влияния на реальную практику

**Второй приоритет: Kleros**

**Обоснование:**
- Уникальная возможность изучить "architectural" аспекты арбитража (экономические стимулы, механизмы)
- Отсутствие необходимости в скрейпинге — данные структурированы по природе
- Риск: неопределённость практической ценности из-за неясного правового статуса; техническая сложность

**Третий приоритет: New TLD**

**Обоснование:**
- Естественное расширение UDRP-анализа на сравнительную плоскость
- Лучше рассматривать как подмножество или второе поле после освоения UDRP

**Четвёртый приоритет: Specific types**

**Обоснование:**
- Требует предварительного корпуса (UDRP или иного) для эмпирической типологии
- Риск circularity: типы должны вытекать из данных, а не предшествовать им

### Необходимые доказательства перед фиксацией поля

**Для UDRP:**
1. **SOURCE ACCESS:** Проверка возможности массового сбора данных с WIPO и NAF без нарушения ToS; оценка структурированности HTML
2. **CORPUS BOUNDARY:** Подсчёт реально доступных кейсов за определённый период; проверка полноты полей (все ли кейсы содержат полный текст решения)
3. **EXISTING SYNTHESIS:** Систематический обзор существующей количественной литературы (не только юридической) для определения gaps
4. **ABILITY TO TEST:** Проверка наличия labeled subset или возможности создания gold standard для валидации

**Для Kleros (альтернатива):**
1. Техническая проверка доступности полных данных через subgraph/IPFS
2. Оценка разнообразия типов споров (не все ли escrow/dispute однотипны)

### Следующее конкретное действие разведки

**ACTION:** Пилотный сбор данных UDRP для проверки SOURCE ACCESS и CORPUS BOUNDARY

**Конкретные шаги:**
1. Разработка скрейпера для WIPO Decisions (ограниченный период: 2020-2024, случайная выборка 100 кейсов)
2. Структурирование полей: case number, domain, parties, panelist(s), provider, outcome, key findings
3. Оценка полноты и консистентности полученных данных
4. Проверка наличия текстов решений (не только метаданных)
5. Документирование технических ограничений и edge cases

**Метрика успеха:** Получение structured dataset ≥90 кейсов с полными текстами решений, пригодного для предварительного анализа паттернов.

**Альтернативное действие (если SOURCE ACCESS для UDRP непреодолим):** Переключение на Kleros с использованием существующих subgraph (например, Klerosboard) для оценки качества и полноты on-chain данных.
