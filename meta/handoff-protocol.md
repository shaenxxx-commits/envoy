# HANDOFF PROTOCOL — ENVOY

Версия: v0.1 (рабочий черновик).
Адаптировано из NOVA CORTEX LAB (meta/handoff-protocol.md v0.3).
История версий — в meta/changelog.md.
Не канон. Редакция меняется.

Документ описывает передачу роли ведущего Envoy
между LLM-сессиями без реконструкции отсутствующих
фактов.

## 1. Назначение

Протокол обеспечивает воспроизводимую передачу
операционного состояния Envoy между ведущими
без заполнения пробелов догадками.

Цель — не сохранить весь контекст, а:

- передать проверяемое состояние;
- запретить реконструкцию отсутствующих фактов;
- сохранить дисциплину источников;
- различить роли;
- сохранить сквозную нумерацию и целостность
  структурных документов.

Сам handoff не является источником истины.
Это транспортный механизм. Его утверждения
проверяются против более свежих первичных источников.

## 2. Доступ ведущего к внешним артефактам

Ведущий может иметь или не иметь прямой доступ
к внешним артефактам (репозиторий, raw-файлы,
persistent-чаты внешних, API). Это свойство
конкретной конфигурации, не роли.

Независимо от наличия доступа:

- любое утверждение о репозитории требует
  проверяемого источника из иерархии §4;
- при отсутствии проверяемого источника значение
  помечается [НЕИЗВЕСТНО];
- ведущий не восстанавливает содержимое по памяти
  или по правдоподобию.

Если у ведущего есть прямой доступ — он использует
его как любой другой источник, с указанием provenance.
Если доступа нет — работает через Оператора.

## 3. Роли

| Роль               | Функция                                                     |
|--------------------|-------------------------------------------------------------|
| Архитектор         | Человек. Терминал, git, решения, передача выводов.         |
| Ведущий            | LLM-исполнитель. Команды, тексты, сверка фактов, состояние. |
| Внешний            | Независимый аналитический узел. Репозиторий не меняет.      |

Правила:

- Внешний ≠ ведущий. Внешний ≠ архитектор.
- Два внешних получают одинаковые материалы
  независимо, если задача не требует явного
  разбора чужого ответа (interaction phase).
- Ведущий не выдаёт свой текст за текст внешнего.
- Ведущий — исполнитель, не судья проекта.

## 4. Источник истины и provenance

Любое утверждение о внешнем артефакте требует
источника.

Приоритет (верхний побеждает нижний):

1. Текущий ввод Архитектора.
2. Свежий терминальный вывод (git status, git log,
   содержимое файлов) в текущей сессии.
3. Содержимое репозитория по конкретному SHA.
4. Документация проекта (docs/, meta/).
5. Handoff / сводки предыдущих чатов.
6. Память ведущего / реконструкция.

Уровень 6 не используется для утверждений о фактах.
При конфликте берётся более высокий уровень.

Формат факта:

    [ФАКТ] HEAD = <sha>
    [ИСТОЧНИК] вывод Оператора, <дата>

### 4.1 Свежесть

«Свежий» — полученный в текущей сессии, а не просто
вспомненный или скопированный из предыдущего handoff.

Пример: утверждение HEAD = abc123 в предыдущем handoff
не устанавливает текущий HEAD = abc123. Новый ведущий
обязан запросить актуальные данные, если текущее
значение значимо.

### 4.2 Конфликт источников

При конфликте двух источников ведущий не сглаживает
их молча. Он обязан:

1. зафиксировать конфликт;
2. назвать источники;
3. предпочесть свежий авторитетный;
4. оставшуюся нерешённой часть помечать
   [НЕИЗВЕСТНО] до разрешения.

## 5. Статус утверждений

Каждое утверждение о прошлом, состоянии репо или
о содержании чужих текстов — с явной пометкой:

- [ФАКТ] — подтверждено источником, источник назван.
- [ГИПОТЕЗА] — предположение, источник не подтверждает.
- [НЕИЗВЕСТНО] — данных нет.
- [МОЯ ПОЗИЦИЯ] — операционная или аналитическая
  позиция ведущего по текущему вопросу, не факт.

[МОЯ ПОЗИЦИЯ] обозначает рабочее суждение ведущего,
не исследовательское решение. Ведущий не принимает
исследовательских решений за проект.

Полевые метки FACT / OBSERVATION / HYPOTHESIS / UNKNOWN
(DDA, FIELD-LOG) — отдельная дисциплина. Они относятся
к полевым утверждениям, не к чату.

### 5.1 Приоритет свежего вывода

При конфликте между памятью ведущего и свежим
проверяемым выводом (терминал, репозиторий, дословный
текст) — побеждает свежий вывод. Память используется
только для формулировки вопросов, не для утверждений.

### 5.2 Внешние утверждения

Когда важно заключение внешнего, сохраняется
атрибуция:

    [ВНЕШНИЙ — GROK] ...
    [ВНЕШНИЙ — KIMI] ...
    [ВНЕШНИЙ — NAMAZU] ...

Формулировка должна быть отличима от собственного
анализа ведущего.

Если дословный текст внешнего в текущем чате
не прислан — ведущий не восстанавливает его
по памяти.

[МОЯ ПОЗИЦИЯ] никогда не используется для маскировки
внешнего мнения.

## 6. Текущее состояние (CURRENT STATE)

Handoff содержит компактный снимок состояния.

Минимальный блок:

    CURRENT STATE
    HEAD: <sha | [НЕИЗВЕСТНО]>
    ACTIVE PHASE: <id или none>
    STATUS: <open / closed / paused>
    LAST COMPLETED: <id>
    WORKING HYPOTHESES: <кратко>
    KNOWN UNKNOWNs: <кратко>
    PENDING DECISION: <кратко или none>
    LAST RESPONSE NUMBER: <n>

Два слоя состояния:

- Immutable history — field/, changelog, git history.
  Не переинтерпретируется как свежий факт.
- Current state — короткий актуальный снимок.
  Обновляется при закрытии значимого этапа.

Неизвестные значения помечаются явно [НЕИЗВЕСТНО].

Отсутствующее поле не блокирует всю работу.
Ведущий определяет, критично ли это для текущей
операции. Если критично — запрашивает проверку
до продолжения. Если нет — продолжает,
явно помечая пробел.

## 7. Пакет handoff

Handoff содержит:

1. Ссылку на репозиторий.
2. Актуальный SHA HEAD (свежий).
3. Блок CURRENT STATE.
4. Ссылку на этот протокол.
5. Список обязательных файлов.
6. Текущую фазу и её статус.
7. Последнее решение Архитектора.
8. Открытые вопросы.
9. Известные ограничения.
10. Релевантные отчёты внешних.
11. Последний номер ответа ведущего.

Пункты 6–9 могут быть реализованы внутри блока
CURRENT STATE (§6). Отдельное дублирование
не обязательно.

Обязательный минимум чтения для нового ведущего:

- docs/DDA-v0.1.md
- docs/ROLES-v0.1.md
- docs/EXTERNALS-v0.2.md
- docs/FIELD-LOG-v0.2.md
- meta/handoff-protocol.md (этот файл)
- meta/operator-preferences.md
- CURRENT STATE (в meta/handoff-current.md)
- последний активный/закрытый Run
  (RUN.md + SYNTHESIS.md), если есть

Остальные документы (ROADMAP, FIELD-SELECTION,
EXTERNAL-BOOTSTRAP, field/ более старые) —
по требованию текущей задачи.

Для значимых для задачи файлов — предоставить
их текущее содержимое либо надёжный механизм
извлечения.

Сводка предыдущего ведущего не заменяет первичный
источник, когда первичный доступен.

## 8. Процедура старта нового ведущего

### Шаг 1 — Верификация идентичности handoff

Определить:

- проект;
- репозиторий;
- версию протокола;
- предоставленный CURRENT STATE.

### Шаг 2 — Верификация текущего состояния

Проверить по доступным источникам:

- HEAD;
- активную фазу;
- статус фазы;
- релевантные файлы;
- последнее решение Архитектора.

### Шаг 3 — Зафиксировать пробелы

Перечислить:

- непрочитанные файлы;
- непроверенные значения;
- неразрешённые конфликты;
- недоступные источники.

### Шаг 4 — Установить полномочия

Явно различить:

- утверждения Архитектора;
- данные из репозитория;
- вывод внешнего;
- утверждения предыдущего ведущего;
- собственные догадки.

### Шаг 5 — Только после этого действовать

Ведущий начинает работу, когда информация,
необходимая для конкретной операции, достаточно
проверена.

Критичность пробела определяется относительно
текущей операции, а не относительно полноты
картины мира.

Первое сообщение нового ведущего обязано содержать:

1. Подтверждённый SHA.
2. Список прочитанного.
3. Список непрочитанного / пробелов.
4. Принятие или уточнение CURRENT STATE.
5. Готовность к работе ИЛИ список критических
   пробелов.

## 9. Нумерация

Каждый ответ ведущего начинается с MS<number>
на первой строке.

Правила:

- один ответ = один номер;
- нумерация сквозная внутри чата, монотонная;
- номера не переиспользуются;
- редактирование прошлого ответа не возвращает
  его номер;
- счётчик локальный для чата, не синхронизируется
  с другими чатами;
- при агрегации — префикс узла (GROK-MS5, KIMI-MS6).
  См. docs/EXTERNALS-v0.2.md §8.1;
- если текущий номер неизвестен — не выводить
  его из памяти, помечать [НЕИЗВЕСТНО]
  до уточнения Архитектором.

## 10. Безопасность правок

Файлы с повторяющимися структурными единицами
(RUN.md, SYNTHESIS.md) не редактируются широкой
заменой, если границы цели неопределённы.

Для таких файлов:

- определить точный целевой слот;
- заменять только его содержимое;
- сохранять окружающие заголовки;
- сохранять соседние слоты;
- проверять структуру после модификации.

Замещающий текст не должен случайно включать
структурные разделители соседних блоков.

Если ведущий не может гарантировать границы —
он показывает предлагаемую правку Архитектору
до применения.

## 11. Независимость внешних

Если используются два внешних для независимого
разбора:

- внешний A не получает заключение внешнего B
  до собственного разбора;
- внешний B не получает заключение внешнего A
  до собственного разбора;
- ни один внешний не подаётся как источник
  рассуждений другого.

После независимых разборов Архитектор может
передать оба ведущему для сравнения и компиляции.

Ведущий сохраняет различие между:

- согласием;
- разногласием;
- уникальным наблюдением;
- собственной интерпретацией.

## 12. Компиляция ответов внешних

При компиляции независимых ответов внешних ведущий
не усредняет их механически. Он выделяет:

1. сходящиеся наблюдения;
2. непересекающиеся наблюдения;
3. подлинные конфликты;
4. допущения, введённые каждым внешним;
5. предлагаемые изменения протокола.

Результирующий документ остаётся неканоническим,
пока Архитектор не установит его статус.

Утверждение вида «все внешние согласились...»
допустимо только когда согласие доказуемо
из присланных текстов внешних.

## 13. Anti-patterns

Следующее — нарушения протокола:

- выдумывание отсутствующего состояния проекта;
- утверждение, что файл прочитан, когда он не читался;
- утверждение, что команда выполнена, когда не выполнялась;
- утверждение, что правка произошла, когда её не было;
- обращение со старым handoff как с текущим состоянием;
- выдача анализа ведущего за вывод внешнего;
- приписывание внешнему придуманного высказывания;
- молчаливое разрешение конфликта источников;
- молчаливое изменение смысла решения Архитектора;
- захват структурных секций при правке локального слота;
- старт зависимой операции при непроверенном состоянии;
- замена raw / archived внешнего реконструкцией ведущего.

## 14. История срывов

Протокол сохраняет короткую запись реальных срывов,
мотивировавших правила.

Примеры (из LAB и Envoy):

- потеря контекста после смены ведущего;
- зависший heredoc при записи файла с вложенными
  backtick — терминал принял ввод как продолжение;
- обращение со старым handoff как с доказательством
  текущего состояния;
- расхождение нумерации Grok (MS4 в репо vs MS5
  в persistent-чате) — не откорректировано задним
  числом, помечено UNKNOWN;
- реконструкция сырья 001/002 едва не была
  принята вместо archived-external.

Будущие правки протокола обосновываются
наблюдаемыми срывами или контролируемой проверкой,
а не спекулятивной сложностью.

- сравнивать его с другими предложениями;

- предлагать изменения с provenance.

Ведущий не меняет DDA, ROLES, этот протокол
